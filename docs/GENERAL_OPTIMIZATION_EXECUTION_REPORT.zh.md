# 通用长上下文优化执行报告

日期：2026-10-15。实施基线：`a731f9c`。实现版本：`0.4.0-beta.1`。依据：[已批准实施计划](GENERAL_OPTIMIZATION_IMPLEMENTATION_PLAN.zh.md)。可提交的脱敏运行摘要：[验收证据](evidence/general-optimization-20261015.json)。完整本地请求、输出和盲评记录保存在被 Git 忽略的 `evaluation/runs/`。

通用执行模块和配套基础设施已实现，已完成受控回归及授权的 `deepseek-flash` 合成样本评测。当前可以作为实验版测试；还不能宣称真实长论文质量与全部发布矩阵通过。受管调用在本次语义样本中仍比直接输出慢，因此默认策略的关键是让模型判断是否需要受管任务，而非把所有请求交给另一轮辅助生成。

## 已实现的正常流程

主模型从原请求、范围、输出关系、依赖和容量判断处理方式。当前上下文足够且不需要持续状态或文件交付时，直接回答；少量阅读不建立任务。需要受管执行时，`lc_work` 冻结约定并执行首批，`lc_continue` 继续；工作单元、证据、依赖、预计输出长度和必要检查由模型决定。没有新增请求分类器、planner 或翻译专用分支。

连续内容、锚点修改和条目集合共用提交与验收。综合使用有界的已处理结果树，允许多对一；无来源创作没有页数或引用下限。主模型已有内容可连同真实阅读凭证直接提交，避免辅助模型重写。准确字面修改完全由程序计算并独立核对预期。

产出调用合并目标自检；冻结的全部或相关范围独立复核不能被自检替代。引用须来自实际可见证据，综合的每层继续校验准确引用。处理覆盖、检查方法和语义质量分别记录，不把 `completed_with_checks` 解释为事实真理。

所有义务满足后内部装配并发布，正常流程不再要求额外扫描、计划、保存报告、逐块复核或最后点击完成。返回短回执与最新 CAS，大结果通过引用分页。预算、调用和实际/估算用量可见；普通状态查询不产生账本事件。

## 实测结果

### 保存与恢复

同机串行比较 Git 基线与本轮通用核心，输入均为 956,291 字节、374,291 个 Unicode 码点、94 个存储块、6,000 次替换。逐字核对候选与独立预期一致，原稿未变，两版模型调用均为 0。100 个合成分隔单元不表示物理页数。

| 指标 | 基线 | 新通用执行 |
| --- | ---: | ---: |
| 修改流程耗时 | 43,335 ms | 670 ms |
| journal 字节 | 260,112,977 | 6,586 |
| journal 事件 | 100 | 5 |
| 调用方变更命令 | 99 | 1 |
| 冷启动完整账本审计恢复 | 3,872 ms | 1 ms（取整） |

journal 减少约 99.997%，该样本总流程耗时减少约 98.5%；完整账本恢复达到计划的 50% 改善门槛。该结果主要来自准确修改的直接计算与增量账本，不是语义模型加速率，也不是统计性能保证。不可变结果、完整审计和原始材料未被删除。

### 真实模型与质量

使用用户授权的原生 `deepseek-official/deepseek-flash`，温度 0、输出上限 4,096、沿用 route 默认推理设置，未强制关闭推理。通用核心与直接调用采用同一适配器；运行串行、样本很小，无统计质量或速度结论。下表为各用例成功执行记录；早期失败仍另行保留。

| 合成请求 | 直接输出 | 受管执行 | 检查结果 |
| --- | --- | --- | --- |
| 短文完整转换 | 1 次，3.62 s | 1 次，7.77 s | 盲评未发现关键遗漏或误改 |
| 全材料综合及指定问题 | 1 次，5.88 s | 1 次，12.49 s | 三个问题及证据限制均保留 |
| 日志条件筛选 | 1 次，2.84 s | 1 次，24.96 s | 只选 A1/A4，边界值 30 不纳入 |
| 定义及远处推导同步修改 | 1 次，2.97 s | 2 次，22.17 s | 当前值与推导修订，历史值保留；受管执行含所要求的独立复核 |
| 10 节重复材料完整转换 | 1 次，15.19 s | 4 次，56.30 s | 最终 10 节均交付，编号、数值与条件无关键遗漏；批次边界有少量额外空行 |

盲评由独立于 DeepSeek 产出的 Codex 在查看匿名 A/B 文本后评分，再打开 route 对照；不是人工专家盲审，也不证明一般领域质量。重复长样本只验证较长输入与分批交付，不能替代跨章节依赖复杂的真实长论文。

受管路径仍有真实开销。直接输出不包含持久范围、恢复、检查和文件副作用，不能为了展示加速将这部分成本藏掉。模型能够一次完成的请求应直接回答；需要受管但主模型已有结果时，应提交已有内容；只有确实需要时才采用辅助批次。

在**实际原生会话**中，短问答及材料已在消息中的转换均观察到 1 个主模型 step、没有通用任务。最后一次 Long Context 输出边界复测未附带运行时权限、技能目录或检查点，保留所要求正文。Standard 对照出现将宿主元数据纳入输出的失败，故不拿该次异常耗时计算插件加速百分比。

失败记录包括：一次网络超时（观测墙钟异常长，不能用作稳定延迟）、旧插件转换调用错误、复杂全量 JSON Schema 提示下较长受管输出耗尽 token。后者促使本轮删除无关结果结构的提示，只描述当前结果结构；相同长样本随后通过。没有以重试后的通过覆盖原失败，也没有把缺失结果记为完成。

## 回归与复核

执行了类型检查、ESLint、构建、打包及真实 rc.2 loader/ToolRuntime 验证。完整套件和新增中断回归的最终数量记录在[证据文件](evidence/general-optimization-20261015.json)。覆盖 owner/CAS/requestId、输入变更、准备结果凭证、预算、依赖失效、引用丢失/伪造、输出外部编辑、快照/历史篡改、v2 迁移与回退、取消迟到结果、模型等待期间其他任务推进、发布/报告写入中断重放，以及原旧任务门槛。

按 code-review 技能完成 Standards/Spec 两轴复核。Standards 未发现硬性标准违规，指出的逐单元重复整篇读取已通过操作内缓存修复，并新增 64 个单元准备的读取次数回归。Spec 复现的两项 P1（综合丢失引用、渲染期间候选被外部修改仍完成）均修复、增加反例测试，并经再次只读复核关闭。

仍未验证用户原始论文、真实 provider overflow、全部取消/HMR/崩溃组合、完整真实 51 篇筛选和长内容物理页数质量矩阵。新通用文字要求依赖标明范围的方法进行语义检查；专业旧协议的强校验不会被泛化为任意条件的程序证明。以上限制保留为发布门槛。

## 运行与交付

`pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm run build`；`pnpm evaluate:general-performance` 复现同机准确修改对比。`pnpm evaluate:general-model` 是授权后才能运行的付费小样本；较长样本可用 `LC_EVAL_CASES=long-mapped LC_EVAL_NATIVE_SKIP=1` 选择。每次有独立目录，保留原始输出、调用/用量、匿名评测和对照表。

本轮打包为 `.acceptance/dsh-long-context-0.4.0-beta.1.tgz` 并安装到隔离验收 profile，没有修改生产默认模型或凭证文件，没有发布 npm/市场。旧截图和此前 Web 部署报告属于旧版本历史，不能作为新三页签界面的视觉验收证据。
